Statistics whose last digit you can check

A command line, in the shape of cancho-table and cancho-ml, that describes data and draws inferences from it: summaries, correlations, tests, intervals, resampling, regression with standard errors. A mean, a variance and a p-value are each printed as one correctly rounded number, with an error bound that was written before the code and measured after it.

Why

A statistics tool answers with numbers people paste into reports. Most of them are sums of floating-point terms, so the last digits depend on the order of the rows, the number of threads and the platform's maths library. Here:

  • Where a sum decides the result, it is exact and rounded once, at the end. The row order cannot change a bit.
  • The same input, seed and arguments give the same bytes at 1 to 16 threads and on every platform the CI workflow covers.
  • Every refusal is data: a rule tag stats.<name>, an exit code, a repair where one is safe. No input reaches a trap.
  • No claim about another library that was not measured here, with the machine and the case count next to it.

The design is docs/design.md. What S0 settled, with the measurements, is docs/numerics.md.

The distribution functions

The p-values rest on lgamma, erf, the regularised incomplete gamma and beta functions and the normal quantile, written in cancho from std.math's own exp and log (no platform libm). From them: normal, Student t, chi-square, F and binomial, each with a survival function that is computed from its own tail, never as 1 - cdf. Real outputs of the built driver:

The last digits of those lines are the honest part: they are within the bound, not equal to the textbook value.

The error bound, written first

For each function and input range, a relative error bound was committed before the first line of the implementation: B(f) = B0 + B1 |ln f|, where the second term is the stated far-tail behaviour (the argument of the last exp carries a rounding error that grows with its size). Measured against mpmath at 60 digits and more, at the exact input doubles:

familybound B0cases per rangeoutsideclosest to the bound
erf, erfc, normal2e-1320,00000.12
incomplete gamma, chi-square2e-13 to 5e-1220,000 (2,000 large)0 after one correction0.97
incomplete beta, t, F, binomial5e-13 to 1e-1120,000 (2,000 large)00.52

Found by the gate. The full-size run found 26 cases up to 1.6 times the bound in the incomplete gamma that the smaller runs missed. The far-tail coefficient was corrected in place from 4e-16 to 1.5e-15 for that family, and the document says so. A ratio of 0.97 means that bound is tight, not comfortable.

The accuracy is bounded only in the stated ranges; between them and the refusal limits the functions answer without a bound. A second reference, scipy.special, is put beside mpmath on 4,000 cases per range: it is never the tie-breaker, and where it is the outlier (the binomial by up to 3.4e-9) the page of results says so.

Exact sums, and how wide

A variance needs sum(x^2) and a covariance sum(x*y). S0 measured how wide an accumulator must be, against fractions.Fraction, on 600 vectors in each of ten families:

methodsum of squaressum of products
plain double, in row orderinexact in 40 to 50% of vectorsup to 1.8e-13 off on cancellation
two-product into faccexact inside a range, silently wrong outside itexact for exponent sums from -997 to 1003; silently wrong beyond
ml.fsq, 4196 bitsexact for every finite doublen/a

The rule that follows: squares go through ml.fsq; products go through the two-product and facc and a value outside 2^-485 ≤ |x| < 2^501 is refused with a named rule and a repair. One rounding, at the end.

The same bytes

A fingerprint of 48 lines (every function on fixed seeded sweeps, the edge cases, the accumulator results) is committed. The built driver prints the same bytes on:

machineequal to the goldenthreads 1, 2, 3, 4, 7, 8, 16
macOS arm64 (the writer)yessame bytes
Linux x86-64 (a clean clone, 7 cores)yessame bytes
GitHub: ubuntu-24.04, ubuntu-24.04-arm, macos-26yes (CI run, no step skipped)same bytes

That shows equal bytes for these sweeps on these machines, nothing about others. One thing the gate caught on the way: the sweeps' own generator called the platform's log, so two machines were comparing different inputs. It is now exact integer arithmetic.

Run it

Everything is pinned: the compiler, cancho-table's exact-sum stores, the contract package of cancho-tools and the 23 numeric stores of cancho-ml, by commit, never copied (sh scripts/check_pins.sh checks that, and 21 mutants show the check can fail).

git clone https://github.com/alpibrusl/cancho-stats.git
cd cancho-stats
export CANCHO=<path-to-the-cancho-binary, the revision in cancho.toml>
"$CANCHO" install
"$CANCHO" build --bin special-check
python3 -m venv .venv && .venv/bin/pip install -r ci/requirements.txt
sh scripts/check.sh            # every gate, minutes
sh scripts/check.sh --full     # also the larger sweeps and the mutants

The driver reads cases on standard input and prints the bits of the answer, so a gate compares bytes, not decimals:

$ echo "1 4000000000000000 4024000000000000" | build/special-check t_sf
1 3fa2c98ee9420ee7 0

(t_sf(2, df 10); the first column is the case id, then the bits of the result, then the refusal code, 0 for an answer.)

Status and limits, stated plainly

  • Built: the special functions, the exact-accumulation decision and its measurement, the pin check, the gates (accuracy sweeps, edges and fuzz, independence, fingerprint, 85 mutants of the special functions: 73 killed and 12 explained), the CI workflow.
  • Not built: every verb. There is no stats binary yet; the page above describes the library under it.
  • The error bounds are measured on seeded samples, not proved, and hold in the ranges stated in the document.
  • Exact variance and covariance need a big-integer multiply that the compiler's library lacks; it is S1's first module.
