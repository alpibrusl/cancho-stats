# Moving the stories generators to cancho (design, written before any code)

Status: design. Nothing here is built. Every claim is marked **[read]** (read in the source today), **[choice]** or **[open]**; none is measured yet, and the measurements that would settle the open points are listed in section 5.

## 1. What exists

Four generators draw four stories pages from real runs of their tool: `scripts/gen_stories.py` (+ `stories_marketing.py`) in cancho-stats, and one each in cancho-table, cancho-ml and cancho-www. They share `scripts/storylib.py` as a **copy** (the same file four times) **[read]**. A generator (1) writes seeded invented data, (2) runs the tool, (3) checks that each narrated claim still holds (`claim`), (4) draws SVG figures and HTML from the JSON the tool printed, and (5) with `--check` compares the regenerated bytes with the committed page.

## 2. Why move them

Python is there for three jobs (section 5 of the discussion that led to this file): independent oracles, mutant harnesses, and these generators. The first two are justified by independence from the code they judge. The generators are not: they are process calls plus templating, and a copied `storylib.py` can drift. A cancho program doing this job is a test of the language on ordinary tooling.

## 3. What cancho already has **[read]**

`std/process.cho` (spawn with argv, pipes, timeout), `std/json.cho`, `std/buffer.cho`, `std/dirs.cho`, `std/io.cho`, `std/fmt.cho`, `std/bignum.cho`. The effect vocabulary lists `file_read`, `file_write`, `dir_read`, `dir_write`, `heap` and the rest; a generator needs the process row and the filesystem rows and no network, so its authority row would be checkable the way the three tools' rows are.

## 4. Decisions

* **One shared library, pinned by commit, never copied** **[choice]**, as `contract/` of `cancho-tools` already is for the three tools. Its content: the claim check, the pretty-printer of JSON, number formatting (fixed decimals, never an exponent: the Python version had to be fixed for this twice), HTML escaping, the SVG axis and figure primitives, the terminal-block and story-section templates, the page skeleton, `--check`.
* **Each generator stays in its repo** and imports the library; the library knows nothing of a tool's data or story.
* **Determinism is the gate** **[choice]**: the cancho generator must write the **same bytes** as the Python one for all four pages before the Python is deleted. That is a comparison that can fail, run on the committed pages.
* **The compiler pins differ** **[read]**: stats builds with a4572ea, table with e47d647, ml with 0207556. A shared library must compile under all three **[open]**; if it cannot, it is pinned per consumer at the oldest revision that builds it.
* **Seeded data generators** (the invented data) need a PRNG whose stream is fixed. `ml.rng` is SplitMix64 and stable **[read]**, but the Python data use `random.Random` seeds (Mersenne Twister) and the pages are built from them. Porting changes every number on every page. **[choice]**: port the data generators last, as a deliberate change that regenerates and re-reviews all pages, not inside the byte-identity gate.
* **Recording stays separate** where the tools cannot run in CI (cancho-www records `data/stories.json`, CI only checks the page against it) **[read]**.

## 5. cancho-ui for the pages?

`cancho-ui` builds JavaScript and DOM that run in the browser; server-side rendering is refused as `unsupported-on-target` and is only a possible Phase 6 **[read]** (`docs/platform-model.md`). So it cannot write the static pages today, and the pages' properties depend on being static: readable without script, indexed by search engines, comparable byte for byte with `--check`. What cancho-ui could do now is **render the figures and the stories on the client from a JSON of the recorded runs**. That is a different product (a viewer), costs the three properties above, and is not proposed. **[open]**: whether an SSR backend should be asked for in cancho-ui; the stories pages would be its first real consumer, and that is the only reason to ask.

## 6. Plan

1. Measure the three open points: (a) the library compiles under the three pinned compilers; (b) `std/process` and `std/json` handle the largest document a run prints (not yet measured); (c) the cost of the SVG primitives written in cancho against the Python ones, in lines.
2. Port the library (`claim`, `pretty`, `num`, `esc`, `axis`, `svg`, `term`, `story`, `fig_hashes`, page skeleton, `--check`), each function against its Python twin on fixed inputs (a table of cases, as for the tools' refusals).
3. Port the cancho-www generator first (it reads JSON and runs nothing: the smallest), byte-identical to the committed `stories.html`.
4. Port stats, table, ml; delete the Python generators and the four copies of `storylib.py` only when their pages are byte-identical.
5. Last, and separately: the data generators.

## 7. Where the library lives **[open]**

`cancho-tools` (where the contract package is) or a new `cancho-storylib` repository. It is outside the repositories this session can write to; that is the maintainer's call and the first thing to settle.
