Six stories, one bakery.

Marta has bought a second oven and wants to know whether it was a good idea. Each story asks a little more of the tool than the last. Every number and every figure below is drawn from a real run of stats on the data you can download. The data are invented, with effects planted on purpose (B bakes faster and rises higher, three of its batches run long, the crust, weight and salt do not differ, A has more defects); the runs are real, and the narration is checked against the numbers whenever the page is generated.

Data (invented, seeded): bakery.csv (80 batches), pilot.csv (the first four batches of each oven). Rebuild this page: python3 scripts/gen_stories.py.

1 · Before anything else, look

start heredescribe

“I bought a second oven. Is it any good?” — Marta, who bakes for a street of cafes

Marta kept a note of every batch for two months: which oven, how many minutes, how high it rose, how the crust scored, whether a loaf came out defective. Eighty batches, forty per oven. Before she asks anything, she looks at the one number she cares about most, the baking time.

2 · Is the new oven faster?

one questiontest t2ci diff

“Eyeballing it, B is quicker. Show me it is not my imagination.”

The textbook answer is Welch’s t test: compare the two means, allow the spreads to differ. The tool prints the statistic, the degrees of freedom, the p-value, an effect size and the interval of the difference. The same interval is available alone with ci diff, byte for byte.

a real run
$ stats test t2 --cols bake_min --group oven bakery.csv
{
  "levels": {"a": "A", "b": "B"},
  "tests": [
    {
      "statistic": 1.8222469060619957,
      "df": 73.1757032479013,
      "p_value": 0.0725033707662692,
      "effect_size": {"name": "cohen_d", "value": 0.4074667953743296},
      "interval": {
        "of": "difference of means",
        "level": 0.95,
        "estimate": 1.9775000000000005,
        "low": -0.18521043371277957,
        "high": 4.140210433712781,
        "rounding": "double"
      },
      "n": {"a": 40, "b": 40}
    }
  ]
}
Reading it. A is 1.98 minutes slower on average, with a 95% interval from -0.185 to 4.14 and p = 0.0725. The interval reaches across zero, so at the 5% level this does not show a difference. (ci diff prints the same interval: -0.185 – 4.14.) Marta is not convinced, and she is not wrong to be careful — but the pictures in story 1 suggested something. What is it that a mean cannot see?

3 · Three loaves ran long

when the data misbehavetest mannwhitneyresample perm

“Three batches in oven B took over fifty minutes. The timer stuck, I think. I did not throw them away.”

Every batch as a dot shows what the means hid: oven B’s typical batch is faster than A’s, and three batches — ringed — are far to the right. A mean is pulled by such points; a test that compares ranks is not. The Mann–Whitney test asks whether a batch from one oven tends to beat a batch from the other. The permutation test below asks the question of the means directly, by shuffling which batch went to which oven.

a real run
$ stats test mannwhitney --cols bake_min --group oven bakery.csv
{
  "tests": [
    {
      "statistic": 1107.0,
      "p_value": 0.0031799854079099642,
      "p_method": "normal",
      "effect_size": {"name": "rank_biserial", "value": 0.38375},
      "n": {"a": 40, "b": 40}
    }
  ]
}
a real run
$ stats resample perm --cols bake_min --group oven --seed 7 --permutations 9999 \
    bakery.csv
{
  "p_method": "monte-carlo",
  "seed": 7,
  "tests": [
    {
      "statistic": 1.9775000000000005,
      "p": 0.0703,
      "extreme": 702,
      "permutations": 9999,
      "mc_error": 0.0025566471489950364
    }
  ]
}
Reading it. The tests that use the mean (both t tests, and the permutation test of the mean difference) all say “not shown”, because three long batches inflate B’s mean and its spread. The rank test, which looks at the bulk of the batches, says p = 0.00318. Neither is “the right one”: they answer different questions, and the answer says which one it answered. The permutation test's count is exact (702 of 9999 shuffles were as extreme; the Monte Carlo error is printed, 0.0026), and every one of those numbers can be reproduced by an independent program from the seed. What Marta now knows: the typical batch of B is faster; the average is dragged by three exceptions she can investigate.

4 · Six questions at once

many tests, one decisiontest t2--correct holm

“While I am at it: height, crust, weight, moisture, salt. Did the new oven change any of them?”

Ask six questions at the 5% level and the chance that at least one comes out “significant” by luck alone is about one in four. The honest way to run a family of tests is to say so up front. --correct holm declares the six tests a family and prints each p-value both as computed and after Holm’s step-down correction; the tool refuses a family larger than --max-tests, so a fishing trip has to be declared.

a real run
$ stats test t2 --cols bake_min,height_cm,crust,weight_g,moisture_pct,salt_pct --group \
    oven --correct holm bakery.csv
{
  "adjustment": "holm",
  "family": {
    "size": 6,
    "correction": "holm",
    "p_adjusted": [
      0.2900134830650768,
      0.0010895185787315627,
      1.0,
      1.0,
      0.0005220022161199081,
      1.0
    ]
  },
  "tests": [
    {"column": "bake_min", "p_value": 0.0725033707662692},
    {"column": "height_cm", "p_value": 0.00021790371574631254},
    {"column": "crust", "p_value": 0.5766632775939438},
    {"column": "weight_g", "p_value": 0.5962294964274081},
    {"column": "moisture_pct", "p_value": 8.700036935331803e-05},
    {"column": "salt_pct", "p_value": 0.6300676855585874}
  ]
}
Reading it. Height and moisture still stand out after the correction; the crust, the weight and the salt do not, and neither does the baking-time mean (the story 3 problem again). The hollow and filled circles are the same test before and after the family is accounted for. Marta can now say which of her improvements are real and which could be six coin flips.

5 · Is it luck? Count it

exact answers to small questionsresample perm --permutations alltest fisher

“In the first week I only had four batches from each oven. Could four and four have told me anything?”

With eight batches, “by luck” can be counted. Hand any four of the eight batches to oven A and the other four to oven B: there are 70 ways. For each, compute the difference of the means; the p-value is the fraction of ways at least as far from zero as the real one. --permutations all does exactly that, and the comparison is made on exact integers, with no tolerance. The first four batches of each oven were 41.2, 38.9, 43.2, 40.8 minutes in A and 33.9, 40.7, 43.5, 42.9 in B: not obviously different, and the count will say how different “not obviously” is.

a real run
$ stats resample perm --cols bake_min --group oven --permutations all pilot.csv
{
  "p_method": "exact",
  "tests": [
    {
      "statistic": 0.7750000000000004,
      "p": 0.8,
      "extreme": 56,
      "permutations": 70,
      "n": {"a": 4, "b": 4, "missing": 0}
    }
  ]
}

Why not do the same on all eighty batches? Because there are about 1023 ways to split them, and the tool says so instead of trying:

a real run
$ stats resample perm --cols bake_min --group oven --permutations all bakery.csv
exit 8
{
  "code": "PRECONDITION_FAILED",
  "rule": "limit.exact-too-large",
  "message": "more arrangements of the labels than the exact test enumerates",
  "hint": "use --permutations N for the Monte Carlo test",
  "detail": {"limit": 1048576, "values": 80}
}
Reading it. 56 of 70 arrangements are as extreme as the real one (the red squares), so p = 0.8 — the exact permutation p-value, not an approximation. Four against four cannot show a difference this small, and the count says so in the plainest way there is. There is no seed in this answer because nothing was drawn.

The same idea decides the yes/no question. Over all eighty batches, 12 of 40 loaves from oven A had a defect and 1 of 40 from B. Fisher’s exact test enumerates every table with the same margins:

a real run
$ stats test fisher --cols defect --vs oven bakery.csv
{
  "tests": [
    {
      "p_value": 0.0014946381722911106,
      "p_method": "exact, probabilities not larger than the observed",
      "effect_size": {"name": "odds_ratio", "value": 0.05982905982905983},
      "assumptions": {
        "levels": {"column": ["n", "y"], "vs": ["A", "B"]},
        "table": [28, 39, 12, 1]
      }
    }
  ]
}
Reading it. p = 0.00149, from enumerating the tables, not from a formula that is only good for large counts: oven B has far fewer defective loaves, and this is the question on which the evidence is clearest. The odds ratio is printed too.

6 · Would anyone get the same numbers?

the point of the tooltest t2resample permsha256

“My accountant will run this on her laptop, and the cafe’s analyst on a server. Will they get my numbers?”

The sums are exact, so the order in which rows are added cannot change a bit; the exact permutation test depends only on which values are in each group. Here is the proof you can run yourself: the same questions on the same data with the rows in three orders, and the SHA-256 of everything the tool printed.

Reading it. All three digests of each question are identical. Across platforms it is the same: the project’s CI runs these answers on Linux x86-64, Linux arm64 and macOS arm64 and compares their hashes to the file docs/xplat_fp.txt. (One thing that does depend on row order, by design: a bootstrap resamples row positions, so ci boot is a function of the file’s bytes and the seed. The answer says so.)
